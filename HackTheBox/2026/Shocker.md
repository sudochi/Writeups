# Shocker – Writeup (Easy)

**Machine:** Shocker  
**Difficulty:** Easy  
**Tech Used:** Nmap, Dirb, Feroxbuster, Metasploit, ShellShock, Perl, Linux privilege escalation  
**Objective:** Demonstrate web enumeration, exploitation of the ShellShock vulnerability, obtaining a user shell, and escalating privileges to root.


**By:** Ce'Bria Haynes |
**Published:** 9/14/2026

---

## Overview

Shocker is an easy-level HackTheBox machine focused on web enumeration, identifying a vulnerable CGI script, exploiting the ShellShock vulnerability, and performing Linux privilege escalation.

The initial Nmap scan revealed two open ports: 80 and 2222. Port 80 was running an HTTP server, while port 2222 was running an alternative OpenSSH service. After adding `shocker.htb` to `/etc/hosts`, I navigated to the website and found a simple webpage containing an image of a bug with the message "Don't Bug Me!"

I performed directory enumeration using Dirb and discovered the `/cgi-bin` directory. Since the directory itself returned a 403 Forbidden response, I used Feroxbuster to enumerate files within it. This discovered a `user.sh` script.

Accessing the script revealed output that appeared to be generated by the Linux `uptime` command, indicating that a Bash script was being executed by the web server. After researching the target, I identified it as vulnerable to CVE-2014-6271, also known as ShellShock.

Using the corresponding Metasploit module, I was able to exploit the vulnerability and obtain a shell as the `shelly` user. I then retrieved the user flag before enumerating `shelly`'s sudo permissions. This revealed that `shelly` could execute Perl as root. Using Perl's ability to execute system commands, I spawned a root Bash shell and retrieved the root flag.

## Enumeration

### Nmap Scan:

I started with a full TCP port scan using Nmap with service detection and default scripts:

```bash
nmap -sC -sV -p- 10.129.69.206 -oA shocker_scan
```

The scan identified two open ports:
```bash
80/tcp    open  HTTP
2222/tcp  open  OpenSSH
```

Port 80 was running an HTTP server, while port 2222 was running an alternative OpenSSH service.

Since the HTTP service was the most obvious attack surface, I added shocker.htb to my /etc/hosts file and navigated to the website.

### ShellShock

The use of a Bash CGI script immediately raised the possibility of the ShellShock vulnerability.

ShellShock, tracked as CVE-2014-6271, is a critical Bash vulnerability discovered in 2014. Under certain conditions, specially crafted environment variables can cause Bash to execute arbitrary commands.

I started Metasploit using:

```bash
msfconsole
```

I then selected the Apache CGI Bash environment variable injection module:

```bash
exploit/multi/http/apache_mod_cgi_bash_env_exec
```
<img width="604" height="288" alt="msfconsole" src="https://github.com/user-attachments/assets/ec6d6500-13ac-459f-b59a-b29a768fa220" />

After setting the required options for the target and payload, I executed the exploit.

The exploit was successful and provided me with a shell on the target as the user:

```bash
shelly
```

### Privilege Escalation

With access as shelly, I checked the user's sudo permissions:

```bash
sudo -l
```
<img width="608" height="150" alt="sudo l" src="https://github.com/user-attachments/assets/9f1ac4c9-f7d8-4927-b692-1d032e4e9737" />

The output showed that shelly could execute perl as root.

Perl's -e option allows Perl code to be executed directly from the command line. Perl can also execute system commands using the exec function.

I used the following command:

```bash
sudo perl -e 'exec "/bin/bash"'
```

<img width="433" height="50" alt="root shell" src="https://github.com/user-attachments/assets/a364ea3d-5fde-498f-afae-c2275b92c03e" />

Because Perl was being executed with root privileges, the Bash shell spawned by the command also ran as root.

I confirmed the new privileges with:

```bash
whoami
```

The result was:

```bash
root
```

This confirmed that I had successfully escalated from shelly to root.

### Root Flag

After obtaining a root shell, I navigated to the /root directory:

```bash
cd /root
```

I listed the contents and retrieved the root flag:


## Conclusion

Shocker demonstrates how an exposed CGI script combined with an outdated Bash installation can lead to complete system compromise.

The initial Nmap scan identified two open ports, with port 80 running an HTTP server and port 2222 running an alternative OpenSSH service. Web enumeration using Dirb discovered the /cgi-bin directory. Although the directory itself returned a 403 response, further enumeration with Feroxbuster revealed the user.sh CGI script.

The output from user.sh indicated that Bash was being used to execute the CGI script. This led to the discovery of the ShellShock vulnerability, CVE-2014-6271. By exploiting the vulnerable Bash environment through the Apache CGI interface, I was able to obtain a shell as shelly.

After retrieving the user flag, I performed local privilege enumeration with sudo -l. This showed that shelly could execute Perl as root. By using Perl's -e option and the exec function to launch /bin/bash, I was able to obtain a root shell.

The main techniques demonstrated by this machine were:

- Full TCP port enumeration with Nmap
-  Web directory enumeration with Dirb
- CGI script enumeration with Feroxbuster
- Identifying a Bash CGI script
- Identifying CVE-2014-6271 ShellShock
- Exploiting ShellShock with Metasploit
- Obtaining a shell as shelly
- Linux privilege enumeration with sudo -l
- Abusing Perl execution as root
- Obtaining a root shell
- Retrieving both the user and root flags

Overall, Shocker is a good demonstration of how a vulnerable CGI configuration can expose a system to remote command execution and how excessive sudo permissions can then be used to escalate from a low-privileged user to full root access.
